# 团队职责与任务协作

更新日期：2026-10-21（北京时间）。

当前安排：**三人共同负责开发修改，两人各自独立进行全系统、全流程测试。** 不按前后端或功能模块固定分人，不沿用此前的人员分配。具体问题由三名开发协商认领，每个问题有一名负责人即可。

当前重点是解决真实使用中的错误和操作不顺畅，同时补齐全部已确认需求。原定交付期限已过，新的完成日期待确认。

## 开发需要做什么

三名开发共同处理以下内容，完整工作清单见[实施任务清单](../requirements/产品体验与待办清单.md)：

- 修复实际使用和测试发现的错误，优先解决流程中断、数据错误、排期不正确、发布或导出失败。
- 检查导入、资料维护、排期、调整、校验、评分、发布及导出，补齐需求中的遗漏。
- 简化操作，减少重复填写、反复切换和重复检查，让用户知道当前状态、哪里有问题以及下一步怎么做。
- 改善加载、等待、保存失败、错误反馈及异常恢复，避免用户重复操作造成重复数据或结果丢失。
- 修复后自测、相互检查代码，提供测试版本和修改说明，并根据测试结果继续修复。

## 两名测试怎么做

**每个人都完整测试整个系统，并各自走完真实使用全流程。** 两人覆盖相同的全部范围，各自记录实际执行结果，不能用另一人的通过结论代替自己的测试。

- 都要使用确认后的完整真实数据，覆盖三类答辩、两个校区及适用的联合排期。
- 都要从用户界面走完导入、配置、生成、查看、调整、重验、发布、导出，并检查其他页面、权限、历史版本和实际 EXE。
- 除功能错误外，也要记录难理解的提示、找不到的入口、重复步骤、等待过久、操作后无反馈和容易误操作的地方。
- 两人各用独立可恢复的测试库，各自保留全系统测试记录；共用一份问题清单，重复问题合并并保留各自发现情况。
- 开发修复后，两人各自在自己的测试环境确认相关结果；交付前两人都在同一最终版本完整复测。

执行范围和记录方式见[真实数据全流程测试与验收](真实数据全流程测试与验收.md)。测试现在就开始，边使用、边记录、边修复、边复测。

## 问题怎么记录和处理

每条问题写清：测试人、版本、所用数据与配置、操作步骤、预期结果、实际结果、截图或日志、负责人、修复和复测结果。体验问题也要写出具体卡住的操作及影响，不能只写“体验不好”。

三名开发协商认领问题，优先修复无法继续操作、数据错误和硬规则错误；同一路径上的重复或繁琐操作同步改进。需求口径不清时向用户／业务负责人确认，不自行降低规则要求。

开发修复并自测后交给两名测试分别确认；失败或仍不顺畅时继续登记处理。两人的测试范围和通过情况分别保留，不能将两个人各测一部分拼成全系统通过。

## 协作只保留必要规则

- 每个问题有一名修复负责人；相同文件或接口同时修改前先沟通。
- 使用独立工作目录和任务分支，分支前缀统一为 feat/、fix/、docs/、chore/，通过 PR 集成，至少一名其他成员检查代码。
- 每轮明确集成版本，测试记录关联版本；开发人员共同协调进度和阻塞。具体认领放在 Issue／任务记录，[STATUS.md](../../STATUS.md)只汇总项目进度。
- agent 产出也要由成员理解、自测和检查；文档与规划任务不自动授权修改业务代码。
- 真实资料、数据库和导出保存在受控的本地忽略目录，测试使用副本，不修改日常业务库。

统一开发规范见 [CONTRIBUTING.md](../../CONTRIBUTING.md)。

## 什么情况下算完成

全部本期需求有实际验收证据；两名测试各自在同一最终版本完成全系统、全流程测试，完整真实数据跑通，无漏排、重复、硬规则绕过及未解决的阻断错误，实际操作顺畅，输出可使用。

使用测试教室的人员验证与实际资源下的可执行排期分别记录；未执行、缺资料或失败项不能算通过。实际 EXE、导出、升级和恢复仍须验证，不能只以源码测试通过作为交付依据。交付执行[测试与发布](测试与发布.md)。
