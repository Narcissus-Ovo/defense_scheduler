# 团队职责与任务协作

确认日期：2026-10-12。团队由老成员 A、B 和新成员 C、D、E 组成。本文规定职责、任务分配、问题处理和验收流程；开发环境、分支与提交规则遵循 [CONTRIBUTING.md](../../CONTRIBUTING.md)。

本期目标为 2026-10-18 00:00 前完成全部已确认需求，10 月 17 日完成最终验收与交付。[实施任务清单](../requirements/产品体验与待办清单-2026-10-12.md)登记待认领任务，[全量需求追踪](../requirements/全量需求追踪.md)登记逐项验收，[STATUS.md](../../STATUS.md)只汇总总体进度、里程碑、阻塞和证据，不登记人员分工。

## 1. 职责与交付记录

| 成员 | 职责 | 应提供的记录 |
| --- | --- | --- |
| A | 管理进度和方向，核对需求，确认 C/D 分工，跟进依赖与阻塞；提供日常技术答疑和基本代码检查；组织最终交付 | 任务范围与验收口径、分工确认、阻塞处理结论、评审意见、项目进度汇总 |
| B | 协助处理 A 无法解决的技术问题；承担最后的技术检查 | 疑难问题的处理建议、关键技术审查结论、需要修复与复查的项目 |
| C、D | 协商开发分工，各自主责认领任务；完成实现、自测、联调和缺陷修复；说明代码改动 | 任务认领、分支与 PR、自测结果、影响范围、问题和修复说明 |
| E | 准备验收场景，持续独立测试，详细记录问题，复测并关闭缺陷，维护逐项验收证据 | 测试场景、版本与结果、缺陷记录、复测结论、需求验收记录 |

A 判断需求是否符合已确认口径；新的业务歧义或范围变化先记录并向用户／业务负责人确认。B 提供技术判断，不能通过技术处理静默放宽业务规则。C/D 对自己的实现和修复负责，E 对实际执行的测试与复测结论负责。

## 2. 任务分配

1. A 与 E 对照 PRD 和现有基线梳理缺口，C/D 提供相关代码与接口现状。
2. C/D 根据技术能力和模块依赖提出分工，A 确认范围、遗漏和接口边界。
3. 每项开发任务指定 C 或 D 中的一名主负责人，另一人可以协助。跨前后端任务也必须有主负责人。
4. 分工确认后登记 Issue 或任务记录，注明 A 的评审责任及 E 的验收责任，再开始实施。
5. 需要换人或调整范围时，更新任务记录并由 A 确认；不能只口头转交。

每个任务至少记录：任务编号、关联需求、目标、允许修改范围、主负责人、评审人、验收人、依赖、目标日期、验收标准、分支／PR、当前状态。

任务状态使用：`待认领 → 进行中 → 待评审 → 待测试 → 已完成`。发现问题进入 `待修复`，修复后进入 `待复测`；无法继续时标为 `阻塞`，同时记录原因、需要谁协助、下一步及跟进时间。实现完成、自测通过和验收通过分别记录。

## 3. 开发与共同修改

- C/D 使用各自的任务分支，统一采用 `feat/`、`fix/`、`docs/`、`chore/` 前缀；遵守同一套提交、评审和验证规则。
- 修改前明确任务边界，不能自行增加功能、改变需求口径或顺带大范围重构。
- 接口字段、共享政策、公共类型、数据库迁移及导出结构发生变化时，先由 A 协调，C/D 确认契约和主修改人。
- 多人或多个 agent 不共用同一份可写工作目录同时修改文件；使用各自 checkout／worktree 和任务分支，通过 PR 集成。
- 提交测试前，开发负责人先自测，记录正常场景及与改动相关的异常、边界场景。E 的独立测试不替代开发自测。
- PR 说明关联任务、改动原因、影响范围、自测结果和剩余问题。普通改动可以由 C/D 相互检查，A 重点核对需求与关键改动；仍遵守至少一名其他成员批准的规则。

所有成员可以使用 agent 辅助工作。每次委托应明确目标、允许修改范围、交付物和验收标准；需求讨论和规划任务不自动授权修改业务代码。任务负责人必须理解、核实并能解释产出，不能仅凭 agent 的“完成”或“测试通过”报告关闭任务。

## 4. 问题处理与技术协助

处理顺序为：开发负责人定位并尝试解决 → 向 A 提交问题 → A 无法解决时向 B 求助。

向 A 或 B 求助时提供：

- 任务／缺陷编号和相关分支、提交版本。
- 最小复现步骤、必要输入和实际错误信息。
- 预期行为与实际行为。
- 已经检查或尝试的方法及结果。
- 需要协助判断的具体问题、影响的任务及期限。

A 负责跟进阻塞和安排处理；不确定的技术或需求结论不写成已解决。协助处理的问题应记录结论、负责人和下一步，不能把“已经求助”视为问题已关闭。影响生成、发布、数据关系或主要操作流程的问题应立即通知 A，尽早安排处理。

## 5. 测试与缺陷记录

E 从任务分配阶段开始准备场景；每项功能具备测试条件后及时测试。测试预期依据 PRD、已确认决定和验收标准，不能仅按现有实现反推正确结果。

每条缺陷使用独立编号，至少包含以下字段：

| 字段 | 记录要求 |
| --- | --- |
| 编号与标题 | 唯一编号，标题描述具体错误 |
| 关联需求／任务 | PRD、UX 或任务编号 |
| 测试环境与版本 | 分支／提交、后端或 EXE 版本、相关环境 |
| 前置条件与输入 | 数据、账号权限、答辩类型、排期版本、配置及随机种子（如有） |
| 复现步骤 | 按顺序写明操作，使他人能重现 |
| 预期与实际结果 | 分别描述，不只写“有问题” |
| 证据 | 截图、日志、接口响应或导出文件；共享材料使用合成／脱敏数据 |
| 严重程度 | 阻断：无法继续、数据损坏或硬规则被绕过；重要：功能错误或遗漏需求；一般：不阻断流程的显示、交互等问题 |
| 负责人和状态 | 指定修复负责人，记录待修复／待复测／已关闭等状态 |
| 修复与复测 | 修复提交、复测版本和日期、实际结果；失败时重新打开 |

E 测试真实后端和实际导出，覆盖三类答辩、两个校区、联排、手调、移动、冲突、权限和历史版本。Mock 测试注明用途，不能替代真实后端验收。缺陷由 C/D 修复；E 核实修复结果后关闭，并检查相关流程是否受影响。

## 6. 日常进度与完成标准

C/D 每天更新任务的已完成内容、下一步和阻塞，并关联可检查的结果。E 更新已测试范围、缺陷和复测结论。A 据此检查遗漏、依赖和期限，将项目层面的进度与阻塞汇总到 STATUS.md。

任务标为“已完成”前必须满足：

1. 约定验收标准全部满足，代码负责人自测通过。
2. 评审意见已处理，相关 PR 已合并到约定主线。
3. E 验收通过，相关缺陷复测关闭；验收版本与交付代码对应。
4. 必要检查通过，相关接口、规则、使用文档及验收记录已同步。
5. A 核对需求结果，并更新项目总体进度。

agent 已生成代码、页面能打开、测试条数较多，都不能单独作为完成依据。

## 7. 最终检查与交付

A 提前与 B 确认最终检查时间，并预留修复、复测和复查时间。提交 B 检查的材料包括代码版本、关键改动、测试与验收结果、已解决疑难问题、未解决问题及已知限制。

- B 重点检查算法与硬约束、导师／秘书关系、联排、权限、发布校验和数据一致性，提出具体结论。
- C/D 修复检查发现的问题，补充必要验证并更新提交记录。
- E 对修复复测，并完成全部 PRD 与新增体验要求的逐项验收及发布回归。
- A 核对需求覆盖、B 的审查结论、E 的验收证据、版本、发布产物和说明，组织最终交付。

B 的最终技术检查不能替代 E 的业务验收。最终交付按[交付计划](../requirements/交付计划-2026-10.md)与[测试发布指南](测试与发布.md)执行，尚未解决的阻断问题不能登记为交付完成。
